# Design

## Context

動機見 proposal.md 的 Why。本文件就是問題清單:每題列出出處、問題、選項和建議。請在「**回答**」那一行填上答案:

- 同意建議:寫「照建議」。
- 選別的選項:寫選項代號,例如「選 b」。
- 都不是:直接寫您的做法。

也可以在對話裡回覆,例如「A1 照建議、A3 選 b」,由 Claude 代填。

## Goals / Non-Goals

**Goals:**

- 第 1 階段要用到的每一個決定都有明確答案,並寫回 `docs/spec/`。

**Non-Goals:**

- 不寫程式,不建立 schema 或範例資料。
- 不處理第 2 階段以後才需要的細節,例如評分權重、高度公式的參數。

## Decisions

### P 流程

#### P1. `docs/spec/` 與 `openspec/specs/` 的分工

- **出處**:CLAUDE.md 寫「規格是唯一依據」。導入 OpenSpec 之後,`openspec/specs/` 也會累積需求,變成兩個來源。
- **選項**:
  - a. `docs/spec/` 仍是唯一依據,給人讀的產品規格。`openspec/specs/` 只放各階段已實作、可測試的需求(SHALL 加 Scenario),每條需求註明出自 `docs/spec/` 哪一節。兩者衝突時以 `docs/spec/` 為準,並停下來問。
  - b. 把 `docs/spec/` 搬進 `openspec/specs/`,改由 OpenSpec 當唯一依據,`docs/spec/` 只留給人讀的導覽。
- **建議**:a。`docs/spec/` 是您寫的設計說明,有理由和例子,不適合拆成 SHALL 條文;OpenSpec 的需求則留給驗收用。
- **回答**:_(待回答)_

#### P2. 開發階段與 change 的對應

- **出處**:CLAUDE.md 寫「每個階段完成後開一個 PR」。另有新規則:同時最多 5 個 active change。
- **選項**:
  - a. 一個階段 = 一個 change = 一個 PR。
  - b. 第 1 階段拆成 3 個 change,依序做:`add-project-scaffold`(專案初始化與 CI)、`add-data-model`(schema 與範例資料)、`add-rule-check`(第 1 層檢查與 CLI)。每個 change 開一個 PR。
- **建議**:a,符合 CLAUDE.md 原本的寫法。第 1 階段如果太大不好審,再改用 b。

### A 規格互相矛盾

#### A1. 影片縮圖的比例

- **出處**:01「影片一律 16:9」,型 22 也標「16:9(影片固定)」。但 02 的圖片角色只有 `main`、`square`、`none`,新聞則也只存 `main` 與 `square` 兩份圖。另外,首頁版位 E 是影音放進型 12 橫式輪播,型 12 標的是「主比例」,本站主比例是 3:2,和 16:9 衝突。
- **選項**:
  - a. 新增圖片角色 `video`,固定 16:9。影音內容類型的新聞則要多提供 `images.video`。型 12、13、22 放影音時用 `video` 角色,其餘照舊用主比例。
  - b. 影音也用網站主比例,也就是 3:2 的縮圖。這等於改寫「影片一律 16:9」的規則。
- **建議**:a。
- **回答**:_(待回答)_

#### A2. 「主比例或 1:1」這類二選一的圖片比例,在哪裡決定

- **出處**:型 03、05、15、23、30、32 標「主比例或 1:1」「1:1 或無圖」。範本沒有欄位可以選,而 01 又規定「圖片比例不可覆寫」。
- **選項**:
  - a. 展示類型的 slot 改寫成允許清單,例如 `image: ["main","square"]`。範本加一個 `imageRole` 欄位,在清單中選定一個;實例不可覆寫。
  - b. 把二選一拆成兩個型,例如 03a、03b。但 01 說「只差主比例算同一型的變體」,這個做法與它衝突。
- **建議**:a。
- **回答**:_(待回答)_

#### A3. 範例首頁版位 D 一跑就會出警告

- **出處**:01 首頁版位 D「熱門排行」是新聞放進型 05。但新聞的建議搭配只有 01、02、03、07、08、09、10,所以第 1 層會列為警告。
- **選項**:
  - a. 維持原樣。範例資料會出現 1 個警告,剛好用來示範警告的效果。
  - b. 把 05 加進新聞的建議搭配。熱門排行本來就是新聞,這樣比較合理。
- **建議**:b。05 是熱門排行的標準型;如果維持 a,每次跑檢查都會出現同一個無意義的警告。
- **回答**:_(待回答)_

#### A4. 版面生成的階段編號

- **選項**:a. 以 CLAUDE.md 為準,把 04 的標題改成「版面生成(第 7 階段)」。b. 不改。

### B 規格沒寫

#### B1. 展示類型其餘屬性的值

- **出處**:01 說每型用 7 個屬性描述,但表格只給名稱、分組、標籤、則數、圖片。排列、強調、圖文關係、文字量、互動和 slots 都沒寫;圖鑑也沒有結構化資料。另外,02 的 JSON 範例沒有「圖文關係」這個欄位。
- **建議**:
  - 補一個 `imageText` 欄位,值為 `stacked`(圖上文下)、`side`(左圖右文)、`overlay`(HTML 疊字)、`none`(無圖)。
  - 38 型的這些屬性由 Claude 依型名和圖鑑推定,在第 1 階段的 PR 裡列成表格,請您逐列確認。
- **回答**:_(待回答)_

#### B2. 型 21~38 還沒定義的響應式設定

- **出處**:01 寫「型 21~38 的手機與電腦排法尚未定義」;02 的補充欄位卻要求每型都存「各斷點的欄數」。
- **選項**:a. schema 允許這兩欄填 `null`,表示尚未定義,第 1 層不檢查。b. 由 Claude 推定數值並填入。
- **建議**:a。不要用推定的數值冒充規格。
- **回答**:_(待回答)_

#### B3. 特殊則數怎麼存

- **出處**:01 展示類型表的這幾格:「不限」(34、37)、「1 + 2–4 條連結」(21)、「1 則圖輯,6–12 張」(16)、「每頁 3–6」(15)、「4–12 個時段」(24)。
- **建議**:
  - 「不限」存成 `max: null`。
  - 型 21 存 `{min:3, max:5}`,也就是主則 1 則加連結 2~4 則。
  - 型 16 的則數算 1 則;新聞則加選填的 `gallery`(1:1 圖片陣列),張數 6~12 另外檢查。
  - 型 15 的範圍指每一頁的則數;範本另存分頁數,總則數 = 分頁數 × 每頁則數。
  - 型 24 的每個時段當成一則新聞則來存。
- **回答**:_(待回答)_

#### B4. 圖片寬高的格式,以及要不要放進第 1 層

- **出處**:02 的補充欄位寫「圖片原始寬高,用來檢查圖檔是否已裁成主比例」,但沒有定格式,也沒說由哪一層檢查。
- **建議**:
  - `images.main` 從字串改成 `{ src, width, height }`,`square` 和 `video` 也一樣。
  - 第 1 層加兩條檢查:寬高比與該角色的比例相差不超過 1%;不得是直式(高大於寬)。
- **回答**:_(待回答)_

#### B5. 標題字數存不存

- **出處**:02 的補充欄位列了「標題字數」,但這個數字可以直接從標題算出來。
- **選項**:
  - a. 另存 `titleLength` 欄位,第 1 層檢查它和標題實際字數一致。
  - b. 不存,需要時由程式從 `title` 算。
- **建議**:b。重複存一份只會多一個可能不一致的地方。
- **回答**:_(待回答)_

#### B6. 首頁哪些版位放側欄

- **出處**:02 和 03 要求頁面宣告欄位配置、實例標明放在主欄或側欄,03 的報告範例也有「左欄 6 塊、右欄 3 塊」,但 01 的首頁配置沒有指定 A~M 哪些放側欄。
- **建議**:頁面設 `columns: [8,4]`。C 即時快訊、D 熱門排行、K 觀點評論放側欄,其餘 10 塊放主欄。
- **回答**:_(待回答)_

#### B7. 網站設定的版面數值

- **出處**:02 的補充欄位要網站設定存各斷點容器寬、字級、行高、平均字寬、間距,但沒有給數值。斷點只有 992px,01 卻提到「平板取中間值」。
- **建議**:
  - 只設 992px 一個斷點,6 種測試寬度各自對應一個容器寬:小於 992px 時,容器寬 = 視窗寬 − 32px;992px 以上,容器寬 = min(視窗寬 − 32px, 1200px)。
  - 字級和間距先填示意值:內文 16px、行高 1.5、中文字寬 1em、則間距 16px、區塊間距 32px。這些都標成示意值,第 4 階段再用渲染量測校正。
- **回答**:_(待回答)_

#### B8. 第 1 層要不要多查規格沒列的項目

- **出處**:03 的第 1 層只列 4 條,02 的檢查規則也只有 4 條。
- **建議**:另加下列幾條,全部算錯誤:
  - 每份資料都要通過 JSON Schema 驗證。
  - 引用的 id 都要存在。
  - 頁面列出的實例和實例標記的頁面要一致。
  - 實例實際放的則數要等於覆寫後的則數(02 的範例寫「實際 6 則」,卻只列了 2 個 id)。
  - 實例所放新聞則的內容類型和分類,要與範本一致。
  - 每則新聞都要有 `main` 與 `square` 兩種裁切。
  - 範本和實例不得出現任何比例欄位。
- **回答**:_(待回答)_

#### B9. `npm run validate` 的結束代碼與輸出格式

- **建議**:
  - 有錯誤時 exit code 1;只有警告時 exit code 0。加 `--strict` 時,警告也回傳 1。
  - 預設輸出文字清單,每行一條,格式為「檔案、id、規則代號、訊息」;加 `--json` 改輸出 JSON。
- **回答**:_(待回答)_

### 不另外問、由 Claude 直接決定的細節

以下如有異議,直接在這裡註明即可:

- 英文 id 命名:
  - 內容類型:`news`、`flash`、`video`、`opinion`、`chart`、`feature`、`promo`。
  - 外觀標籤:`image`、`text`、`mixed`、`carousel`、`zoom`。
  - 用途分組:`news-combo`、`av`、`data`、`text-led`、`interactive`。分組不用 `text`,避免和外觀標籤的 `text` 混淆。
- `data/` 的檔案切法:一個 prototype 放一個資料夾,一筆資料一個 JSON 檔。
- 工具:Ajv(JSON Schema 2020-12)、tsx、ESLint flat config 加 typescript-eslint。CI 跑 Node 20 與 22。
- README 只改標題,其他內文不動。

## Risks / Trade-offs

- [答案改動規格文件] → `docs/spec/` 的修改在 PR 裡逐段審閱,只改答案涉及的段落。
- [B1 的推定值可能和您的設計意圖不同] → 第 1 階段 PR 會附 38 型屬性表,請您逐列確認,確認前標為「推定」。
