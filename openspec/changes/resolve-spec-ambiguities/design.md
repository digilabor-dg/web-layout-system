## Context

動機見 proposal.md 的 Why。本文件就是問題清單:每題列出出處、問題、選項和建議。請在「**回答**」那一行填上答案:

## Goals / Non-Goals

**Goals:**

- 第 1 階段要用到的每一個決定都有明確答案,並寫回 `docs/spec/`。

**Non-Goals:**

- 不寫程式,不建立 schema 或範例資料。
- 不處理第 2 階段以後才需要的細節,例如評分權重、高度公式的參數。

- **出處**:CLAUDE.md 寫「規格是唯一依據」。導入 OpenSpec 之後,`openspec/specs/` 也會累積需求,變成兩個來源。

### A 規格互相矛盾

- **回答**:🧑‍🚀 A

### B 規格沒寫

#### B1. 展示類型其餘屬性的值

- **出處**:01 說每型用 7 個屬性描述,但表格只給名稱、分組、標籤、則數、圖片。排列、強調、圖文關係、文字量、互動和 slots 都沒寫;圖鑑也沒有結構化資料。另外,02 的 JSON 範例沒有「圖文關係」這個欄位。
- **建議**:
  - 補一個 `imageText` 欄位,值為 `stacked`(圖上文下)、`side`(左圖右文)、`overlay`(HTML 疊字)、`none`(無圖)。
  - 38 型的這些屬性由 Claude 依型名和圖鑑推定,在第 1 階段的 PR 裡列成表格,請您逐列確認。
- **回答**: 依建議

#### B2. 型 21~38 還沒定義的響應式設定

- **出處**:01 寫「型 21~38 的手機與電腦排法尚未定義」;02 的補充欄位卻要求每型都存「各斷點的欄數」。
- **選項**:a. schema 允許這兩欄填 `null`,表示尚未定義,第 1 層不檢查。b. 由 Claude 推定數值並填入。
- **建議**:a。不要用推定的數值冒充規格。
- **回答**:🧑‍🚀 A

#### B3. 特殊則數怎麼存

- **出處**:01 展示類型表的這幾格:「不限」(34、37)、「1 + 2–4 條連結」(21)、「1 則圖輯,6–12 張」(16)、「每頁 3–6」(15)、「4–12 個時段」(24)。
- **建議**:
  - 「不限」存成 `max: null`。
  - 型 21 存 `{min:3, max:5}`,也就是主則 1 則加連結 2~4 則。
  - 型 16 的則數算 1 則;新聞則加選填的 `gallery`(1:1 圖片陣列),張數 6~12 另外檢查。
  - 型 15 的範圍指每一頁的則數;範本另存分頁數,總則數 = 分頁數 × 每頁則數。
  - 型 24 的每個時段當成一則新聞則來存。
- **回答**:🧑‍🚀 先依建議， 事實上每種編排都非完美，還有很多發展空間，所以才有後面的：生成/評估/反饋

#### B4. 圖片寬高的格式,以及要不要放進第 1 層

- **出處**:02 的補充欄位寫「圖片原始寬高,用來檢查圖檔是否已裁成主比例」,但沒有定格式,也沒說由哪一層檢查。
- **建議**:
  - `images.main` 從字串改成 `{ src, width, height }`,`square` 和 `video` 也一樣。
  - 第 1 層加兩條檢查:寬高比與該角色的比例相差不超過 1%;不得是直式(高大於寬)。
- **回答**: 🧑‍🚀 先依建議，之後再思考怎麼做， 問：既然有square,video,那3：2叫什麼？photograph?

#### B5. 標題字數存不存

- **出處**:02 的補充欄位列了「標題字數」,但這個數字可以直接從標題算出來。
- **選項**:
  - a. 另存 `titleLength` 欄位,第 1 層檢查它和標題實際字數一致。
  - b. 不存,需要時由程式從 `title` 算。
- **建議**:b。重複存一份只會多一個可能不一致的地方。
- **回答**: 🧑‍🚀 A或B, 可能需要定個標準， 評估內容太多或太少怎麼處理？

#### B6. 首頁哪些版位放側欄

- **出處**:02 和 03 要求頁面宣告欄位配置、實例標明放在主欄或側欄,03 的報告範例也有「左欄 6 塊、右欄 3 塊」,但 01 的首頁配置沒有指定 A~M 哪些放側欄。
- **建議**:頁面設 `columns: [8,4]`。C 即時快訊、D 熱門排行、K 觀點評論放側欄,其餘 10 塊放主欄。
- **回答**:🧑‍🚀 可依建議，但實務上會有多個sections,每個sections有不同欄數，比例，及是否fluid?
  - 延伸：一頁中的block可用ABC編號，裡面的第幾項則為序數，
  - 如：A,B,C...Z blocks, A1,A2,A3...A12 items of block A
  - 也可以BLOCK分sections, 如：sections: ABC , Blocks: AA,AB,AC,BA,BB,BC, item: AA3, BA5
  - 這個部份可引用一些 atomic design：https://atomicdesign.bradfrost.com/

#### B7. 網站設定的版面數值

- **出處**:02 的補充欄位要網站設定存各斷點容器寬、字級、行高、平均字寬、間距,但沒有給數值。斷點只有 992px,01 卻提到「平板取中間值」。
- **建議**:
  - 只設 992px 一個斷點,6 種測試寬度各自對應一個容器寬:小於 992px 時,容器寬 = 視窗寬 − 32px;992px 以上,容器寬 = min(視窗寬 − 32px, 1200px)。
  - 字級和間距先填示意值:內文 16px、行高 1.5、中文字寬 1em、則間距 16px、區塊間距 32px。這些都標成示意值,第 4 階段再用渲染量測校正。
- **回答**: 🧑‍🚀 斷點可採用Bootstrap 5.X or Tailwind CSS,原則上只採：desktop, mobile, tablet-H, tablet-V
  - 可直接提供預設參數組：bootstrap5(bs5), tailwindcss(tw4), tailwind預設12 columns, 或參考daisy ui? shadcn?有沒有較具體規範
  - 不綁在哪個框架，只取其參數定義。

#### B8. 第 1 層要不要多查規格沒列的項目

- **出處**:03 的第 1 層只列 4 條,02 的檢查規則也只有 4 條。
- **建議**:另加下列幾條,全部算錯誤:
  - 每份資料都要通過 JSON Schema 驗證。
  - 引用的 id 都要存在。
  - 頁面列出的實例和實例標記的頁面要一致。
  - 實例實際放的則數要等於覆寫後的則數(02 的範例寫「實際 6 則」,卻只列了 2 個 id)。
  - 實例所放新聞則的內容類型和分類,要與範本一致。
  - 每則新聞都要有 `main` 與 `square` 兩種裁切。
  - 範本和實例不得出現任何比例欄位。
- **回答**: 🧑‍🚀 暫依建議

#### B9. `npm run validate` 的結束代碼與輸出格式

- **建議**:
  - 有錯誤時 exit code 1;只有警告時 exit code 0。加 `--strict` 時,警告也回傳 1。

### P1 選 B:改由 `openspec/specs/` 當唯一依據

這個決定改的是流程本身:

- CLAUDE.md 的「規格是唯一依據(`docs/spec/`)」要改寫。
- 原本 tasks 2.1「把答案寫回 `docs/spec/`」不做了。答案改寫成 spec 需求。

我建議**分階段搬移,不要一次全搬**:

- OpenSpec 的 `specs/` 記錄的是「系統現在已經做到的事」。如果第 2~7 階段的內容現在就搬進去,specs 裡會寫著還沒實作的功能。
- 做法:每個階段的 change,把該階段用到的 `docs/spec/` 段落,連同本輪的決定,寫成 spec delta。archive 之後,這些內容才正式進 `specs/`。
- 還沒搬的部分,暫時仍以 `docs/spec/` 為參考;之後 `docs/spec/` 就成為您說的「發想與資料收集」。

### B4:3:2 叫什麼?

建議維持 `main`,不要叫 `photograph`。圖片角色是依「用途」命名,不是依比例:

- `main`:網站主比例。平面站是 3:2,影視站是 16:9。
- `square`:固定 1:1。
- `video`:固定 16:9。

如果叫 `photograph`,換成影視站時名稱就不對了。3:2 只是平面站 `main` 的值,寫在 SiteProfile 裡。

### B5:內容太多或太少的標準

- 第 1 階段我建議選 b:標題字數不另存,需要時由程式從 `title` 算。
- 「太多或太少」不必另訂新標準,規格已經有兩把尺,第 2 階段用標題字數加欄寬估算即可:
  - **太多**:看標題行數,`03` 規定一般 ≤ 2 行、手機 ≤ 3 行。
  - **太少**:看填充率,`05` 規定 60%~90%。
- 之後如果想在存檔時就擋掉過長的標題(例如依文字量設字數上限),可以另開一個 change 再加。

### B6:sections、編號與 Atomic Design

方向我贊成:一頁分成多個 section,每個 section 有自己的欄配置(12、8:4、6:6、4:4:4)與 fluid 設定。這比現在「整頁一個 8:4」實際得多。

不過這個改動不小,我有兩個建議:

1. **section 直接寫在 Page 裡,不另立 prototype**,和「選稿規則寫在範本裡」的做法一樣。prototype 維持 9 種。實例原本標「主欄或側欄」,改成標「第幾個 section 的第幾欄」。
2. **編號:版位代號在整頁唯一,不帶 section 字母。**
   - 也就是維持 A~M,section 另用 S1、S2…,則用版位代號加序數(H1~H6)。
   - 理由:04 的候選改法有「主欄與側欄互換」。如果用 AA、BA 這種兩碼,版位一換 section 代號就跟著變,報告和前後比對都會對不上。單字母 26 個也夠用,規格說 18 塊就算偏長。

對應 Atomic Design 的話:

| Atomic | 本系統 |
| --- | --- |
| atom | 標題、圖片、META |
| molecule | 一張卡片(一則新聞的呈現) |
| organism | 區塊實例(依展示類型排出來的一塊) |
| template | 頁面的 section 與欄配置(不含內容) |
| page | 放入實際新聞的頁面 |

有一個要注意的術語撞名:我們的「區塊範本 BlockTemplate」對應的是 organism,不是 Atomic 的 template。文件裡要寫清楚,避免混淆。

### B7:斷點預設組

我查了各框架的參數:

| 裝置 | bs5 | tw4 | 6 種測試寬度 |
| --- | --- | --- | --- |
| mobile | < 768 | < 768 | 360、390 |
| tablet-V | 768–991 | 768–1023 | 768 |
| tablet-H | 992–1199 | 1024–1279 | 1024 |
| desktop | ≥ 1200 | ≥ 1280 | 1280、1440 |

- **兩組都能把現有 6 種測試寬度剛好分進 4 類**,所以測試寬度不用改。
- 主切換點就是 tablet-H 的起點:bs5 是 992,與現在的規格相同;tw4 是 1024。
- 兩組的格線都是 12 欄。差在欄距(bs5 1.5rem,tw4 沒有預設值)和容器寬(bs5 最寬 1320,tw4 最寬到 1536)。
- daisyUI 和 shadcn/ui 都直接沿用 Tailwind 的斷點,沒有自己的版面規範,不必另做預設組。
- 如果想要「每種裝置幾欄、邊距多少」寫得更具體的規範,Material Design 的 window size classes 比較完整,可以當第三組參考。
- 字級、行高、字寬,框架都不管,仍由網站設定自己填。

### 目標預想對第 1 階段的影響

「headless、JSON 定義一切、之後移植到 Python 或 C#」這個目標,我會在第 1 階段落實成三件事:

- **JSON Schema 當跨語言的合約**:Python 和 C# 都有現成的驗證器可以直接讀。
- **測試寫成「輸入 JSON + 預期違規清單 JSON」的 fixture**:日後移植時,整組測試可以直接沿用,當成相容性測試。
- **核心邏輯不碰 Node 專屬的 API**:CLI 只是外面薄薄一層。
