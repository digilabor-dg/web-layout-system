# POC 1:JSON 估算 vs 實際渲染

範例首頁 13 塊,在 6 種測試寬度比較「`height-estimation` 公式估出來的高度」與「瀏覽器實際排出來的高度」。

```bash
npm run poc:1
```

```bash
npm run poc:1 -- --check-determinism
```

- 產出:`RESULTS.md`(報告)、`results.json`(原始數字)、`screenshots/`(390px 與 1280px)。
- 字型:Noto Sans TC 400(`@fontsource/noto-sans-tc`,OFL)。

## 做法

| 檔案 | 內容 |
| --- | --- |
| `model.ts` | 共用的排法描述:每塊在每類裝置是格線、清單、左右並排還是輪播,幾欄、多寬 |
| `estimate.ts` | 依公式估算區塊高度;盒模型常數與 CSS 一一對應 |
| `text.ts` | 標題行數:`ratio`(規格公式 ⌈總寬 ÷ 欄寬⌉)與 `greedy`(逐字排入,英數字不拆) |
| `render.ts` | 產生 RWD 的 HTML;圖框用 `aspect-ratio` 佔位框 |
| `run.ts` | Playwright 量測、比對、敏感度實驗 |
| `report.ts` | 驗收指標與 `RESULTS.md` |

## 結論

1. **公式的算術是對的。** 格線、左右並排、輪播的寬高推算,與瀏覽器一致到小數點(誤差 < 0.1px)。
2. **標題行數可以估到 100%,但有兩個前提:**
   - **要有三類字寬**:全形 1 em、英數字 0.55 em,以及半形標點與空白(實測 0.22~0.34 em,取 0.3 em)。第一輪只有兩類字寬時,半形標點被當成英數字寬,10 個標題多估一行,區塊高度最大誤差 13.8%。
   - **要用逐字排入(greedy)**。規格的 ⌈總寬 ÷ 欄寬⌉ 正確率 99.2%,差在英文單字不能拆開。
3. **字型和設定不符時仍然穩健。** 估算參數不變、渲染改用另一種字型,標題正確率 99.7%,區塊高度最大誤差 6%。原因是中文在兩種字型都是 1 em,差異只出在英數字。
4. **限制:** 渲染器是照同一套盒模型寫的,所以這個 POC 證明的是「公式與瀏覽器排版一致」,**不是**「公式能套用到任意網站的真實 CSS」。真實模板要等第 4 階段量測才知道。

## 截圖看得出的版面問題(交給 POC 2 的評分)

- **K 觀點評論**:側欄的 4 張 1:1 大圖疊成一長條;P17 的「作者卡」需要「頭像尺寸」的概念,不應該是滿寬的方圖。
- **I 專題**:左圖右文,右側文字遠低於圖高,就是 `05` 範例一的「密度不足」。
- **M 短影音**:電腦上一次顯示 6 張,但只有 4 則,右側留白。
- **F、G、H**:連續 3 塊都是 P09,「同型不連續」會不合格。

## 給第 2 階段的建議

- 網站設定的 `avgCharWidth` 增加 `narrow`(半形標點與空白)。
- 標題行數改用 greedy,規格的 ratio 公式保留成快速估算。
- P17 增加頭像尺寸的參數,或改成左圖右文。
- 輪播增加「則數少於一次顯示張數」的檢查。
