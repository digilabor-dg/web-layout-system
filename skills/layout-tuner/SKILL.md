# layout-tuner:版面調參迴圈

本 skill 驅動 `web-layout-system` 的 CLI。分工(規格 `openspec/specs/ai-review`):

- **程式負責**:分數、判定、候選改法。同樣的輸入一定得到同樣的結果。
- **你負責**:讀報告與截圖、判斷哪些問題真的要改(包括不平衡是不是刻意的)、把數字翻成「改哪裡、為什麼」、提出參數修改。
- **你不可以**:自行給分或改判定;未經使用者確認就覆寫既有的參數檔或 `data/`。

## 步驟

### 1. 確認輸入

問清楚使用者要處理哪一組參數(`poc/generator/params/<名稱>.json`)。沒有的話:

- 請使用者用瀏覽器開 `poc/generator/form.html` 填表產生,或
- 從 `poc/generator/params/default.json` 複製一份再改。

參數格式見 `poc/generator/params.schema.json`。

### 2. 產生並評分

```bash
npm run -s poc:generate -- poc/generator/params/<名稱>.json
```

需要 Chromium(渲染量測與截圖)。環境沒有瀏覽器時加 `--json-only`,但要告訴使用者:比例、可用性兩個面向不會評分。

產出在 `poc/generator/results/<名稱>/`:

| 檔案 | 用途 |
| --- | --- |
| `report.json` | 分數與每個項目 × 對象的判定(格式見 `poc/evaluate/report.schema.json`) |
| `generated.json` | 參數、每塊選了什麼(`choices`)、搜尋紀錄、產生的頁面、範本、實例 |
| `screenshots/page-390.jpg`、`page-1280.jpg` | 手機與電腦截圖 |
| `report.html` | 給人看的 Lighthouse 式報表 |

### 3. 讀報告

1. 讀 `report.json` 的 `total`、`scores`、`pageVerdict`。
2. 列出 `verdict` 不是 `pass` 的 `findings`,依 `item` 分組;引用 `display` 的原文數字,不要自己換算。
3. `target` 是版位代號(會隨位置變動),`ref` 是穩定的實例 id。要跟使用者溝通時用代號,要比對前後時用 `ref`。

### 4. 看截圖,判斷要不要改

用 Read 開兩張截圖。對每個問題判斷:

- **刻意的不平衡**:例如頭條區故意加重、側欄本來就比較短。是刻意的就說明理由,建議保留,不要硬改。
- **評估器漏掉的問題**:目前已知的漏洞(見下方「已知限制」),在截圖上看到要主動指出。
- **圖內文字、海報式圖卡**:程式看不到,只有你看得到。

### 5. 提出參數修改

依下表把問題對應到參數。只提**參數層級**能做到的改法;做不到的要明說原因與替代方案。

| 報告中的問題 | 可以改的參數 | 說明 |
| --- | --- | --- |
| 欄高(某個 stack section 兩欄不平衡) | `sidebar`、`blocks` 的順序、`columns` | 較高的那欄搬一塊到另一欄;或把較矮那欄的區塊換個位置;或改欄比(8:4 → 9:3 讓側欄變窄、變高) |
| 同型不連續 | `blocks` 的順序 | 把同型的兩塊中間插入別的區塊 |
| 放大型不相鄰 | `blocks` 的順序 | 把放大型(頭條、P09、P14 等)分開 |
| 區塊長度(手機太長) | `fullWidth`、`blocks` | 產生器會自己減則數或改輪播;仍太長時,考慮拿掉該區塊 |
| 區塊數、整頁則數 | `blocks` | 增減區塊 |
| 單塊不重複 | `blocks` | 頭條、熱門、快訊各只能一塊 |
| 觸控目標、間距節奏 | (網站設定) | 參數改不到,屬於 `data/site-profile/`。請使用者決定是否調整,例如區塊標題列加高到 48px |
| 欄底對齊(P09)、填充率(P14) | — | 已知的型式限制,參數內無解。說明即可,或建議不要用該型 |

每個建議都寫成:**改哪裡 → 改成什麼 → 為什麼(引用報告的數字)**,並附上修改後的參數 JSON 差異。

### 6. 經人確認後重跑

使用者同意後:

1. **另存新檔**,例如 `poc/generator/params/<名稱>-v2.json`,`name` 也改成 `<名稱>-v2`。不要覆寫原檔。
2. 重跑第 2 步。
3. 比較前後:

```bash
npm run -s poc:compare -- <名稱> <名稱>-v2
```

4. 回報總分、面向與項目的變化,直接引用比較工具的輸出。分數沒變好時要照實說,並分析原因。

### 7. 收尾

- 列出還沒解決的問題,以及原因:型式限制、評估器漏洞或網站設定。
- 需要改網站設定、`data/` 或評估規則時,只提建議,交給使用者決定。

## 雙評分對齊:讓評估器跟上人的感覺

程式不可能一次做到人想要的,所以要用人評(以及 AI 擬人評分)和程式分數對齊,差距最大的地方,就是評估器下一步要補的。

### A. 收集評分

- **真人**:先產生檢視工具。

  ```bash
  npm run -s poc:review
  ```

  請使用者用瀏覽器開 `poc/rating/review.html`:
  - 中間是預覽,側欄可以切換裝置。
  - **評分模式**:點選區塊,給 0~10 分(5 顆星)與短評,盲評。
  - **A/B 模式**:切換或並排兩版,選比較好的一版;說不出原因也沒關係。

  使用者下載 JSON 後,存到 `poc/rating/reviews/`。

- **AI 擬人評分**:`agents/` 有 8 個角色(4 種專家、4 種讀者),各自用盲評版評分集(`poc/rating/sets/<名稱>/manifest.blind.json`)與 A/B 盲測圖(`poc/rating/ab-blind/`)評分。要評新的版面時,先產生評分集:

  ```bash
  npm run -s poc:rating -- <產生結果名稱>
  ```

  再用 Agent 工具,讓每個角色讀自己的定義檔照做。**擬人評分只用來找盲點,不能取代真人,也不是分數。**

### B. 對齊

```bash
npm run -s poc:align
```

讀 `poc/rating/ALIGNMENT.md`:

- **A/B 一致率**:程式分數較高的那一版,評分者是否也選它。
- **區塊評分**:每個版面、每位評分者和程式分數的等級相關與平均差距。
- **盲點**:評分比程式低 3 分以上,評估器可能漏了問題。
- **可能的誤判**:評分比程式高 3 分以上,評估器可能太嚴。

### C. 把短評轉成可量化的反饋

1. 對每一則盲點的短評,依 `docs/wiki/評估.md` 的項目與 `openspec/specs/improvement-suggestions` 的問題類型對照表(例如「右邊太空」對到填充率或欄高),判斷它對應哪個**現有評估項目**,寫進 `mapped`。
2. 對不上任何項目時,不要硬套;寫一個**新項目候選** `candidate`,包括名稱、量法、建議門檻。
3. 存成 `poc/feedback/entries/<名稱>.json`(格式見 `poc/feedback/feedback.schema.json`),然後執行:

   ```bash
   npm run -s poc:feedback
   ```

   覆蓋率 = 對應項目在報告裡確實有問題的「不喜歡」÷ 全部「不喜歡」。同一塊剛好有別的問題,不算覆蓋。
4. 回報覆蓋率、未覆蓋的反饋與新項目候選。新增評估項目會改變所有分數,**只提建議,由使用者決定**。

## 已知限制(2026-11 的 POC)

- **電腦版沒有區塊長度限制**:產生器可能選出全寬、方圖超大的排法(例如觀點評論 P17 在全寬下用清單),分數卻很高。看截圖時特別注意。
- **偏好 P07**:評估沒有獎勵版面變化的項目,產生器容易選出很多 P07 均分圖卡。
- **P09 欄底對齊、P14 填充率、純文字側欄的欄高**:三種寬度互相牽制,參數內無解。
- **平板推算**:「電腦欄數減一」在寬平板上偏保守。

細節見 `docs/wiki/發現與型式限制.md`。
