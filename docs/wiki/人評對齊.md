# 人評對齊(雙評分)

> 狀態:🧪 POC(持續主線,見 [CLAUDE.md](../../CLAUDE.md) 的開發階段)。正式規格(暫名 `score-calibration`)待確認後再寫。

**程式或 AI 都不可能一次做到人想要的。**所以讓人和程式各打一次分數,放在同一個尺度上比對;差距最大的地方,就是評估器下一步要補的。

## 三種評分來源

| 來源 | 怎麼收 | 用途 |
| --- | --- | --- |
| **程式** | 評估報告換算:每塊 10 分起算,不合格扣 3、警告扣 1 | 被校正的對象 |
| **真人** | 檢視工具 `poc/rating/review.html` | 校正的依據 |
| **AI 擬人** | `agents/` 的 12 個角色(見下表) | 真人評分還不多時,先用來找盲點;**不能取代真人,也不是分數** |

### 12 個 AI 角色

角色依 UX 研究與感官評估的方法分類(對照見[反饋收集的發想](../brainstorm/feedback-collection.md)):

| 方法 | 角色 | 看什麼 |
| --- | --- | --- |
| 喜好測試(一般讀者) | 通勤讀者、電腦讀者、年長讀者、快速掃讀者、**平板讀者** | 手機與電腦截圖;平板讀者看 768px |
| 專家意見 | 新聞編輯、視覺設計師、可用性與無障礙專家、前端工程師 | 手機與電腦截圖 |
| 啟發式評估 | **UX 研究員** | 依 Nielsen 十大原則逐塊檢查,標嚴重度 0~4 |
| 五秒測試 | **初次造訪者** | 只憑第一眼的印象 |
| 描述型分析、JAR 量表 | **受訓評估員** | 不評喜好,只給數量、大小、圖↔字、空↔擠、層級 5 條軸的 −5~+5 |

粗體是新增的 4 個角色;第一、二輪只有前 8 個。新角色第一次評分(修正渲染器後的版面):

- UX 研究員與初次造訪者的 A/B 各 8 / 9 和程式一致;範例 07 也都選 V1,現在是 0 / 10。
- 平板讀者最低的是 K 觀點評論與 D 熱門排行,說法是「平板上像放大的手機版,一屏只看得到一兩則」。
- 受訓評估員偏離 0 最多的是:K 電腦版的大小 +4、G 與 J 電腦版的空 ↔ 擠 −3(太空)。這是第一批方向型資料。

## 檢視工具

```bash
npm run poc:review
```

用瀏覽器開 `poc/rating/review.html`(單一檔案,不需要伺服器):

- **中間是預覽**:把 JSON 渲染成的真實網頁。
- **側欄是工具**:
  - 裝置切換:手機 390、平板 768、筆電 1280、桌機 1440。
  - **評分**:在預覽上點選區塊(像 F12 的 inspector),給 0~10 分(5 顆星,半顆 = 1 分)與短評。採盲評,評完才揭曉程式分數。
  - **A/B 比較**:切換(按 A、B、空白鍵)或並排兩版,選比較好的一版。很多人說不出哪裡有問題,但比得出來。左右依題號單雙交替,避免位置偏差;選完才揭曉是哪一版。
  - 匯出評分 JSON,存到 `poc/rating/reviews/`。

## 對齊

```bash
npm run poc:align
```

結果在 [`poc/rating/ALIGNMENT.md`](../../poc/rating/ALIGNMENT.md):

- **A/B 一致率**:程式分數較高的那一版,評分者是否也選它。這是檢驗評估器最直接的指標。
- **區塊評分**:每位評分者和程式分數的等級相關、平均差距。
- **盲點**:評分比程式低 3 分以上,評估器可能漏了問題。
- **可能的誤判**:評分比程式高 3 分以上,評估器可能太嚴。

## 把短評變成可量化的東西

短評很難直接量化,所以交給 skill(`skills/layout-tuner`)轉換:

1. 把每則短評對應到**現有的評估項目**,例如「最後一則孤零零的」對到「末列不落單」。
2. 對不上的,提出**新項目候選**,包括名稱、量法、門檻,例如「平板區塊長度」。
3. 程式計算**覆蓋率**:對應項目在報告裡確實有問題的「不喜歡」÷ 全部「不喜歡」。同一塊剛好有別的問題,不算覆蓋。

```bash
npm run poc:feedback
```

**第一批示範**是範例 02 在 768px 的 3 句擬人評估,覆蓋率 **1 / 3**:

- 「次頭條最後一則孤零零的」:✅ 被「末列不落單」覆蓋。
- 「改完圖片變好大,要滑很久」:❌ 新項目候選「區塊長度(平板)」。
- 「影音焦點只露出一張半」:❌ 新項目候選「輪播露出比例(平板)」。

## 第一輪結果:8 個 AI 角色

> AI 擬人評估,只用來找盲點,不能取代真人。數字在 [`ALIGNMENT.md`](../../poc/rating/ALIGNMENT.md),短評的對應在 [`default-personas.json`](../../poc/feedback/entries/default-personas.json)。

### A/B:76% 和程式一致

10 組範例的 V1 / V2,8 個角色各選一次。有分出勝負的 75 題中,**57 題**和程式選的一樣。

| 範例 | 同意 / 不同意 | 怎麼解讀 |
| --- | --- | --- |
| 03、04、05、08、09 | 8 / 0 | 改善看得出來 |
| 02 | 7 / 1 | 少數人在意區塊變長 |
| 06 | 2 / 1(5 人說差不多) | 觸控目標的差別肉眼幾乎看不到,這是預期的 |
| 01、10 | 3 / 5、5 / 3 | 不同意的人都說:V2 的政治區改成左圖右文,每則只有一行字,右邊大片留白 |
| **07** | **0 / 8** | 見下方 |

**範例 07 全部不同意。**V1 是「整頁 83 則,超過上限」,V2 回到原本的 61 則。但原本的短影音只有 4 則,電腦一次顯示 6 張,右邊空一截(範例 04 修的就是這個);V1 多塞的則數剛好把它填滿。

- 角色看得到「右邊空一塊」,看不到「則數太多」。
- 這組範例混了兩個變因,不是好的 A/B。
- 也代表**「整頁則數」這類編輯規則,和「看得到的留白」該怎麼比重**,需要您決定。

### 區塊評分:和程式分數幾乎無關

示意首頁(預設參數)13 塊,8 個角色和程式分數的等級相關在 **−0.18 ~ 0.22** 之間。程式分數只看得到它有的項目,角色看到的問題很多不在項目裡。

### 盲點對應:覆蓋率 30%

比程式低 3 分以上的短評共 30 則,加上第一批的 3 則,覆蓋率 **10 / 33**。skill 把對不上的歸成新項目候選:

| 候選 | 則數 | 例句 | 性質 |
| --- | --- | --- | --- |
| 內容完整性 | 8 | 「叫排行卻沒有名次數字」「作者卡看不到作者名與頭像」 | **渲染器的 bug**,先修渲染器 |
| 區塊長度(電腦、平板) | 7 | 「電腦版四張大方圖直疊,拉得極長」 | 和 POC 3 發現的漏洞相同 |
| 圖文比(電腦) | 3 | 「一大片圖只換到一則標題」 | 新項目 |
| 填充率(左圖右文清單) | 2 | 「四則都只一行字,圖右邊大片留白」 | 新項目;範例 01、10 的反對意見也是這個 |
| 輪播露出比例 | 2 | 「只露一小條下一張且標題被截」 | 新項目 |
| 疊字對比 | 1 | 「白字疊在漸層淺處」 | 新項目 |

已覆蓋的 10 則:「末列不落單」9 則(B 只有 3 則卻排 4 欄)、「填充率」1 則。

## 第二輪:修正渲染器後重評

第一圈「找到盲點 → 修正 → 重評」。渲染器補上排行名次與作者名(見[發現與型式限制](發現與型式限制.md)),其他都不變;8 個角色在不知道改了什麼的情況下,重評同一個版面。第一輪的評分集保存在 `poc/rating/sets/default-r1/`。

| | 第一輪 | 第二輪 |
| --- | --- | --- |
| 提到「沒有名次」或「看不到作者」的短評 | **13 則** | **0 則** |
| D 熱門排行的平均分 | 3.88 | 4.25 |
| K 觀點評論的平均分 | 2.50 | 2.75 |
| 全部 13 塊的平均分 | 5.56 | 5.56 |

**怎麼解讀:**

- **修正有效,但不是主因。**抱怨消失了,分數卻只升 0.3 左右。第二輪的短評幾乎都在講「方圖太大」(D)和「電腦版拉得太長」(K)。這兩項評估器都還沒有,在[待確認](待確認.md)等您決定。
- **重評的雜訊約 ±0.5 分。**沒改的 11 塊,平均分變動都在 0.5 分以內,整體平均完全不變。換成統計的說法:單一角色的最小可偵測變化(95%)是 1.47 分,8 個角色平均是 0.52 分(算法見[數學與演算法](../brainstorm/math.md)第 9 節)。盲點的門檻差 3 分,遠大於雜訊;D、K 的升幅則小於 0.52 分,不能算改善。
- **新的意見**(第一輪較少提到):
  - 同一頁 4 塊都是 P07 均分圖卡(4 位角色提到),和產生器偏好單調型的問題相同。
  - 名次和縮圖之間空太開(8 位都提到):這是這次修正帶進來的樣式問題,下一輪再調。
  - 「即時」的時間軸沒有時間、標題末行只剩一個字、灰色小字對年長讀者太小、手機輪播看不出可以滑。

## 構想:更好給的反饋

現在的檢視工具是「點選區塊、給 0~10 分」。下一步的構想寫在發想文件 [反饋收集](../brainstorm/feedback-collection.md),還不是規格:

- **圈選任意區域**,也可以圈空白;程式自動對到區塊或鄰近的元素。
- **方向型量表**:例如「圖多一點 ↔ 字多一點」「太空 ↔ 太擠」,0 是剛好。不只說好不好,還說往哪邊改。
- **從短評萃取**軸、方向與程度。
- **猜他想說什麼**:圈下去就列出最可能的 3~5 個讓他確認;或先問 3 題,再依回答問下 3 題。
- **「這樣會不會更好?」**:直接給幾個只改一件事的改法讓他挑,像驗光一樣收斂。
- 收得夠多以後,從評價由負轉正的位置,找出每種展示類型「剛好」的數字,當評估器的門檻。

這些大多有成熟的理論,例如感官評估的 JAR 量表與懲罰分析、語意差異量表、感性工學、適性測驗;發想文件裡有對照表。

## 這套系統如何讓評估器成長

```
產生版型 → 程式評分 ─┐
                    ├→ 對齊:盲點、誤判、A/B 一致率 → 新項目候選 / 調門檻 → 重新評分
真人 / AI 角色評分 ──┘
```

每一輪都看兩個數字有沒有上升:**A/B 一致率**與**覆蓋率**。
